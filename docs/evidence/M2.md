## 2 and 3. Killing the primary promotes the standby with no manual step; the restarted old primary rejoins as a standby; never more than one primary

`make failover-drill` (scripts/failover-drill.sh), three runs in a row, alternating direction. The
script SIGKILLs the primary, polls `pgstatus` about every 1.5 s, starts the old primary again, and
fails if any poll sees two primaries.

`grep -E '^==' docs/evidence/m2-drill-*.txt` (the `docs/evidence/` prefix is cut and the lines
are sorted by run here; nothing else is changed)

```

m2-drill-1.txt:== pg2 promoted 13.4 s after the kill
m2-drill-1.txt:== pg1 container state after kill: exited restarts=0
m2-drill-1.txt:== starting pg1 again
m2-drill-1.txt:== result: promote_seconds=13.4 rejoin_seconds=4.8 max_primaries_seen=1
m2-drill-2.txt:== primary is pg2; killing it with SIGKILL
```

The rejoin goes through the fencing rule and `pg_rewind`:
`docker logs blastradius-pg1-1 2>&1 | grep -E "pg_rewind command|NODE REJOIN"`

```
DETAIL: pg_rewind command is "/usr/lib/postgresql/17/bin/pg_rewind -D '/var/lib/postgresql/data/pgdata' --source-server='host=pg2 user=repmgr dbname=repmgr connect_timeout=2'"
NOTICE: NODE REJOIN successful
```

Docker restart policy: a container killed with `docker compose kill -s SIGKILL` stayed `exited`
with `restarts=0` under `restart: unless-stopped` in all three runs (lines above), so the old
primary comes back only when something starts it.

An earlier build in this session was also drilled under 30 RPS k6 load (not saved to a file):
`promote_seconds=13.4 rejoin_seconds=6.2 max_primaries_seen=1`. The API has no retries or breaker
yet (M3), so client errors during that window were expected and not measured.

### Stale old primary boots first (found in review, fixed, then proven)

`make stale-primary-drill` (scripts/stale-primary-drill.sh): fail over, write a row on the new
primary, stop it, start only the stale old primary, then start the newer node.

`grep -E '^==|entrypoint' docs/evidence/m2-stale-primary-drill.txt`

```
== primary is pg2; killing it and leaving it down
== writing a row through the API on the new primary pg1
== stopping pg1, then starting only the stale pg2
== starting pg1 (newer timeline); pg2 must yield and rejoin
== entrypoint decisions
entrypoint[pg1]: stopping
entrypoint[pg1]: peer pg2 is primary on an older timeline: starting as primary, the peer will yield
entrypoint[pg1]: ready
entrypoint[pg2]: peer is not a primary: starting in last role (primary)
entrypoint[pg2]: ready
entrypoint[pg2]: two primaries: this node yields and will rejoin on restart
entrypoint[pg2]: stopping
entrypoint[pg2]: peer pg1 is primary: rejoining as standby
entrypoint[pg2]: ready
== row written after the failover: {"seqs":[1],"writer_id":"stale-drill-1794813820"}
== result: PASS (pg1 kept the primary role, pg2 rejoined, row survived)
```

Honest limit: in this scenario two primaries do exist for up to about 2 s (the check interval)
until the stale one yields. See docs/QUESTIONS.md item 22 and ADR 0002.
